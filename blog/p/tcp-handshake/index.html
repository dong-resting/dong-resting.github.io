抓之前先清空

Wireshark 里过滤 tcp.flags.syn == 1 or tcp.flags.ack == 1，然后把浏览器缓存清掉，否则你会抓到一堆复用连接的包，看不到握手。

更省事的办法是直接用 curl 访问一个确定会新建连接的小站：

curl -v http://example.com/ -o /dev/null

三个包

帧方向flagsseqack
1客户端 → 服务端SYN0（相对）—
2服务端 → 客户端SYN, ACK0（相对）1
3客户端 → 服务端ACK11

Wireshark 默认显示相对序号，所以看到的是 0 和 1。关掉相对序号（Edit → Preferences → Protocols → TCP → Relative sequence numbers）就能看到真实的 32 位随机值。

握手同时在谈三件事

很多人只记得「同步序号」，但三个包里其实塞了四类信息：

  1. 序号同步：双方各自告诉对方自己的初始序号（ISN）；
  2. 能力协商：MSS、窗口缩放、SACK、时间戳，都在 SYN 的选项里；
  3. 窗口通告：我能接收多少字节；
  4. MSS 决定分片：典型 1460 字节，正好是 1500 MTU 减去 20 IP 头与 20 TCP 头。

为什么 ISN 要随机

如果 ISN 可预测，攻击者可以伪造源 IP 并猜测序号，把数据注入已有连接。现代内核用基于时钟的算法生成 ISN。

常见异常

  • 只看到 SYN，没有 SYN+ACK：对方没监听，或被防火墙丢包；
  • SYN 重传间隔递增：典型的丢包，1s、2s、4s；
  • SYN+ACK 后客户端直接 RST：通常是端口已经关闭，或中间设备改包；
  • 握手成功但立刻 FIN：应用层拒绝，比如 TLS 版本不匹配。

和抓包无关的一句

理解握手不是为了背三个包，而是为了看懂重传、拥塞窗口和 TIME_WAIT 为什么会那样表现。
